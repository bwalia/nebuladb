Recreating a NebulaDB follower PVC on a larger node

We copied a ~20 GB leader snapshot onto the within-region follower. The transfer finished. The pod still died with exit 137. The fix was not another bootstrap — it was deleting a local-path PVC pinned to a 32 Gi node.

Exit 137OOM-kill during snapshot recovery
32 Gifollower limit on debian002
96 Gileader limit (same corpus)

Prod cluster, 18–19 November 2026. Full ops procedure: docs/technotes/follower-pvc-recreate.md.

The misleading success

NebulaDB’s within-region follower is a warm standby for the leader. Compaction means it cannot catch up from WAL alone after a long gap, so we bootstrap it from a leader .nsnap with scripts/bootstrap_region_mirror.sh.

On 18 November that script did its job: freeze a private copy of the live snapshot on the leader, SHA-256 it, stream every chunk to the follower PVC, seed the resume cursor, scale the Deployment to 1. Then verification failed with container not found ("server") — because the server container was already in CrashLoopBackOff.

Logs showed the familiar boot line: listening on :8080, serving 503 until recovery completes. Minutes later, exit 137. That is the kernel OOM-killer, not a corrupt snapshot.

Why 32 Gi was never enough

NebulaDB keeps the working index in RAM. A follower that holds the full corpus needs roughly the same working set as the leader, plus headroom for snapshot load peaks. Our prod leader is capped at 96 Gi. The follower Deployment still said 32 Gi.

RoleMemory limitNodeAllocatable RAM (approx.)
Leader96 Gidebworker00~128 Gi
Follower32 Gidebian002~32 Gi
region-b56 Gidebian004~64 Gi

Raising the follower limit alone would not have helped. The data volume uses Kubernetes local-path storage. Once bound, the PVC is annotated with the selected node. Ours was pinned to debian002 — a machine that simply does not have 64 Gi free.

The rule: recreate the PVC

local-path volumes do not migrate. To put the follower on a larger node you must:

  1. Scale the follower to 0 (stop the crash loop).
  2. Delete nebuladb-follower-data.
  3. Point the Deployment at a node with enough allocatable RAM (nodeSelector / affinity) and raise the memory limit (64 Gi+).
  4. Let a new empty PVC bind on that node.
  5. Run bootstrap_region_mirror.sh again from the leader.
  6. Wait for /healthz to leave 503 and for the showcase peer probe (/peer/follower/healthz) to succeed.

Skip deleting the PVC and you get either another OOM on the small node, or a Pending pod fighting volume affinity.

What we parked, and what “done” looks like

We left ha.withinRegion.followers: 0 behaviour in place operationally — replicas at 0 — so debian002 stopped thrashing and neighbouring workloads stayed stable. The leader kept serving.

Bring-back is complete when: the new PVC’s selected-node is the large machine, the follower Pod is Ready, healthz returns 200 (not endless 503), and RSS sits comfortably under the new limit after recovery.

Lessons

  • Bootstrap success ≠ follower health. Chunk SHA checks prove the bytes landed; recovery still needs RAM to load them.
  • Match peer RAM to the leader’s limit, not to last week’s RSS. Snapshot peaks are higher.
  • Treat local-path node pins as part of capacity planning. Chart comments already warned about debian002; the incident made the recreate steps explicit.
  • Disk-backed document bodies (design 0014) will shrink heap per doc, but they will not remove the need for a large HNSW working set on every full replica.

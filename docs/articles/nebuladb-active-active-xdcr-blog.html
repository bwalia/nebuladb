If your vector database “multi-region” story is either a cold standby or a fake map with six glowing nodes, you do not have active-active — you have a slide. NebulaDB’s production shape is simpler and more honest: each region accepts writes for buckets it homes; XDCR replicates both ways; reads work locally everywhere. The same bucket is not writable in two regions at once.

You can see the live topology on showcase.nebuladb.net — Cluster and Rebalance bind to real /admin/cluster/nodes and /admin/replication APIs, and RAG / Talent Match run against the local index after replication catches up.

Why home region exists

Large HNSW corpuses do not rewind from a compacted WAL tip. A late peer needs a snapshot bootstrap, then incremental XDCR. Pinning each bucket to one home region gives a single writer, local reads everywhere after apply, and failover that is “re-home the bucket” rather than inventing multi-master merge for embeddings.

How it works

  1. Seed metadata sets home_region / home_epoch.
  2. Wrong-region writes get wrong_home_region.
  3. Home leader appends WAL; followers catch up inside the region.
  4. Peer regions apply via bidirectional XDCR.
  5. RAG and vector search run on any region’s local index.

East and west can both be “active” for the cluster: east homes some buckets, west homes others. Neither side silently dual-writes the same bucket.

What we prove in prod

  1. Snapshot-bootstrap nebuladb-region-b so west holds the full east corpus.
  2. Seed homes so some buckets write east, some west.
  3. Prove convergence east→west and west→east (and the wrong-home reject).
  4. Show live peers in the Cluster tab — lag_bytes, behind, remotes.

Scenarios that matter

  • Write in east, RAG in west once lag is quiet.
  • Split affinity — catalogue west, ingest east.
  • Follower loss — promote/practise carefully; snapshot if the PVC is empty.
  • Partition — each region keeps home writes; converge on heal.

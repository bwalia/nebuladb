Most “multi-region database” demos are either a primary with a cold standby, or a slide that pretends every region can write the same key at once. NebulaDB takes a third path that matches how large vector corpora actually behave: each region accepts writes for the buckets it homes, XDCR replicates both ways, and reads work locally everywhere. The same bucket is not writable in two regions at once.

This long article walks through the model, the production topology behind showcase.nebuladb.net, concrete scenarios (RAG, catalogue, failover, partitions), and what you should see in the live Cluster and RAG tabs. The companion technote lives in the NebulaDB repo at docs/technotes/active-active-xdcr.md.

The problem with “write anywhere” for vectors

A hybrid document + vector store is not a tiny key-value cache. Production corpuses on NebulaDB run to millions of documents with HNSW indexes measured in gigabytes. WAL segments compact. A peer that joins late cannot rebuild history from the live tip alone — it needs a full .nsnap bootstrap, then incremental replication.

If two regions accept writes to the same bucket without a merge story, you inherit last-writer-wins across oceans, conflicting embeddings, and opaque “who is authoritative?” incidents. Pinning home region per bucket keeps a single writer while still giving every region a local read replica via bidirectional XDCR.

How it works in sixty seconds

  1. Home region is stored on the bucket seed document (home_region, home_epoch).
  2. Middleware rejects writes when NEBULA_REGION ≠ home (wrong_home_region).
  3. The home leader WAL-appends and fans out within the region to followers.
  4. XDCR tails owned writes to peer-region leaders; they apply into the local index.
  5. Clients read and run vector / RAG queries against any healthy region’s local index.
  6. Failover re-homes the bucket (bump epoch) after the target region is caught up — it is not “open dual writers.”
                    ┌─ us-east-1 (home: catalog) ─┐
  writes (home) ──▶ │ leader ──▶ follower         │
                    │    │  XDCR (bidirectional)  │
                    └────┼────────────────────────┘
                         ▼
                    ┌─ us-west-2 (home: logs) ────┐
  reads (any)  ◀── │ leader ──▶ local HNSW       │
                    └─────────────────────────────┘

This is active-active at the cluster level: every region serves all reads; every region accepts writes for its home buckets. It is deliberately not multi-master for a single bucket.

What runs in production today

On the Workstation k3s ring used by the public showcase:

  • East — nebuladb leader + nebuladb-follower (NEBULA_REGION=us-east-1).
  • West — nebuladb-region-b (NEBULA_REGION=us-west-2).
  • Showcase nginx exposes /peer/follower and /peer/region-b for admin paths.
  • The Cluster and Rebalance tabs call live admin APIs only.

Healthy signals operators care about:

  • Follower /healthz/caught-up → 200.
  • GET /api/v1/admin/replication remotes with healthy: true after traffic.
  • GET /api/v1/admin/cluster/nodes peers listed with real health — the UI you screenshot for docs.

Bootstrapping west (why snapshot first)

XDCR streams new WAL. It does not resurrect compacted history. If west’s document count is a tiny fraction of east’s, you are looking at an empty (or partial) index sitting at a WAL tip that already matches — TailWal has nothing left to replay.

The fix is explicit:

export KUBECONFIG=~/.kube/k3s1.yaml
NS=prod SOURCE=nebuladb TARGET=nebuladb-region-b \
  ./scripts/bootstrap_region_mirror.sh

Operational detail that bites in production: piping a multi-gigabyte .nsnap through kubectl exec often truncates. Prefer chunked dd, node-local copy, or object storage, then write the follower/region cursor to the leader tip. The HA runbook documents the failure mode and the recovery path.

After bootstrap, seed home_region so some buckets write in east and some in west. Prove both directions with a small document each way, and prove the negative path: a wrong-home write must return wrong_home_region.

Scenario walkthroughs

1. East write, west RAG

Home a knowledge-base bucket in east. Ingest (or use an existing corpus). Wait until replication lag on the Cluster tab is near zero. Open the showcase RAG tab — or call vector search — against the west peer path. Retrieval and generation run on the local west index; you are not shipping every query across the ocean.

Streaming RAG on NebulaDB emits context chunks before answer tokens over SSE. That makes multi-region behaviour visible: once west has applied the WAL records, chunk provenance and latency look local even though the write landed in east.

2. Split domain affinity

Catalogue writes home in west; regulatory ingest homes in east. Showcase demos such as Shop Catalog and Companies House stay useful as product surfaces while the write path stays pinned. Product teams get regional write locality without inventing a second database.

3. Talent match / enterprise search

Semantic retrieval demos (Talent Match, Enterprise Search) are the same physics as RAG: embed query, HNSW search, rank. Run the query on both regions after convergence; scores should match within normal float noise once lag is quiet.

4. Within-region follower loss

Delete the east follower pod. The leader keeps serving. The Deployment recreates the follower. For a multi-million-document corpus, if the new PVC is empty but the cursor already sits at tip, snapshot-bootstrap again — do not wait forever for WAL that no longer exists.

5. Cross-region partition

Break east↔west connectivity. Each region continues local reads and home-bucket writes. On heal, lag rises then falls. Because only one region wrote each bucket, there is no CRDT merge ceremony — apply order is the home WAL order.

6. Wrong-home client

Point a mistaken client at west for an east-home bucket. The API returns a structured error with home_region, home_epoch, and node_region. Gateways and SDKs should refresh the home map from GET /admin/bucket/:bucket/home-region rather than retrying blindly.

7. Re-home / failover

When an entire home region is lost (or you are practising), catch the surviving region up, bump home_epoch, set the new home_region, and stop accepting writes on the deposed side. Within-region promote (POST /admin/promote on the follower) remains a separate lever for east HA and is exposed carefully in the Cluster tab.

Comparison to Couchbase XDCR (mental model)

Couchbase XDCR popularised filtered, topology-aware replication between clusters. NebulaDB borrows the intuition — declare where writes land, replicate elsewhere, observe lag — while staying native to WAL + snapshot recovery for an AI-native hybrid store (documents, HNSW, SQL with semantic_match, streaming RAG in one binary).

What we deliberately do not claim: conflict-free concurrent writers on one bucket, automatic magic backfill of compacted history, or Raft quorum across regions. Within-region HA is leader + follower WAL tail; cross-region is XDCR + home pinning.

Operator checklist (copy/paste)

  1. Snapshot-bootstrap nebuladb-region-b until west ≈ east corpus.
  2. Seed home_region for east-home and west-home demo buckets.
  3. Write east → read west; write west → read east; wrong-home write fails.
  4. Open Cluster tab — live peers and remotes, lag visible.
  5. Run RAG / Talent Match on both sides after convergence.
  6. Confirm Grafana panels and alerts still scrape showcase metrics.

Who this is for

Platform teams who need regional read locality for RAG and search without pretending every write can land everywhere. Product engineers building on the showcase demos who need the honest story behind Cluster and Rebalance. SREs who would rather snapshot-bootstrap once than debug a silent empty index forever.

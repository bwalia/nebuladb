# Jira Triage Agent (showcase)

Showcase tab **Jira Triage Agent** (`#/tab/jiraagent`), code in `apps/showcase/src/labs/jira/`.

A manager points the agent at a Jira project and one field: the custom **Priority Score** (1–100, 100 = most urgent). This is not Jira's built-in Priority (Highest/High/Medium/Low), which the agent shows but never ranks by. After every daily or weekly run the agent:

- emails the manager what is **new** (with a score), what moved **up** or **down**, and what was **resolved**, with the reason from the ticket's changelog;
- ranks tickets **relative to each other**. "#1 of 15 (the highest)", a new #1, "the top score jumped from 58 to 95, so the rest of the backlog is relatively lower priority", and "its score rose but it slipped in the ranking because other tickets rose further";
- checks each new ticket against existing tickets with vector search, and flags a likely duplicate or suggests an owning team;
- keeps the score **history** as a Confluence table, with one column per run, a heat map, a trend line and the change since the last run. It can be exported as Confluence storage format or CSV;
- answers questions such as "why did GRO-881 jump?" or "what dropped this week?" from the tickets, with citations.

## Demo data: three fictional companies

| Project | Company | Business | Story in the data |
|---|---|---|---|
| `TIX` | Encore Tickets | live-events ticket marketplace | Stadium tour on-sale: queue token bug goes 62 → 95, bot rules, drip-pricing fix from Legal, duplicate wallet bug raised by support, payment provider incident on Sunday night |
| `PAY` | Harbour Bank | UK retail bank | APP scam reimbursement climbs 46 → 58 → 71 → 88 as the backlog grows; contactless incident hits 94 on Friday's daily run and is 68 by Monday's weekly run; card-freeze bug becomes the new #1 overnight |
| `GRO` | Freshway | supermarket online shop | Everything is low priority (top score 58), then **Christmas slot booking times out → 95** and becomes #1 by 37 points; allergen pages jump 57 → 86 on the next daily run |

There are 50 tickets, and each carries its Priority Score changelog (when the score changed, who changed it and their comment), the way Jira's `expand=changelog` returns it. The agent's stored snapshots are computed from that changelog as if it had run every Monday at 07:00 for eight weeks and every weekday morning for the last week. `data.ts` holds the tickets; `buildCorpus()` builds the 89 docs (50 tickets + 3 projects × 13 runs) seeded into bucket `lab_jira`.

## How a run works

| Step | Who | What |
|---|---|---|
| `load_tickets` | NebulaDB SQL | `kind = 'ticket' AND project = 'GRO'`: every ticket with its score changelog |
| `load_snapshots` | NebulaDB SQL | `kind = 'snapshot' AND project = 'GRO' AND array_contains(cadence, 'weekly')`: one doc per stored run |
| `diff` | code | the chosen run vs the one before it: new, up, down, resolved, rank moves, new leader, scale shift |
| `find_similar` | NebulaDB vector search | for each new ticket, `semantic_match(text, summary + description)` within the project |
| `write_summary` | LLM | the opening paragraph only, written from numbered facts |

The email's tables (new, moved up, moved down, resolved, top 10 with rank arrows) are generated by code. The model never writes them.

## Guards on the LLM paragraph

Production runs `llama3.2:3b`. A model that size gets a lot right, but it often states a direction wrongly with every number correct, for example "PAY-2231 eased off from 71 to 88". Every number passes a number check, so the agent checks more than numbers:

1. **Number check**: every number must be in a fact. If one isn't, the model rewrites once.
2. **Direction check**: each clause that names a ticket and says it rose, fell, was unchanged, is the top ticket, replaced the top ticket or was resolved is checked against the computed diff. If a clause fails, the model rewrites once and is told what the data actually says.
3. **Removal**: any sentence still wrong after the rewrite is left out of the email, along with a "This ticket…" sentence that followed it. If less than half the paragraph survives, the email uses a paragraph built from the facts alone.
4. **Citation check**: a sentence's cited facts together must contain every ticket key and number in it. If they don't, code points the citation at the fact that does and shows the chip dashed.

Every check is shown under the email ("Where the opening paragraph came from"), including the removed sentences and the reason each was removed.

### Examples on prod (`llama3.2:3b`, 10 Nov 2026)

| Run | First draft | What the checks did |
|---|---|---|
| GRO weekly | "…and GRO-735 has remained stable." | Data says 40 → 43; the model rewrote it as "GRO-735 has risen to 43." |
| TIX weekly | "TIX-1199 has eased off to #6, with its score increasing to 76." (and the same for TIX-1174, TIX-1209, TIX-1214) | All four are wrong. After the rewrite the sentences still wrong were left out. |
| PAY daily 6 Nov | "PAY-2231 eased off from 71 to 88, indicating a decrease in urgency." | Caught: the score rose and the rank went from #3 to #2. |
| PAY daily 10 Nov | "PAY-2290 was previously unchanged but has now scored 90" | Caught: it's a new ticket. A sentence with an invented 85 was also removed. |
| GRO daily 10 Nov | "The top priority is now GRO-790 with a score of 86" | Caught: GRO-790 is #2. Too little survived, so the email used the facts paragraph. |
| GRO weekly (number check) | "…jumped by 37 points" | 37 (95 − 58) is not in any fact, so it was rewritten without it. |

Questions in the Ask box get the same number and citation checks. "What is the office parking policy?" returns the fixed reply "The Jira data I checked doesn't cover that."

### Duplicate thresholds

Distances were calibrated on prod's `nomic-embed-text` (lower is closer):

| Pair | Distance | Label |
|---|---|---|
| TIX-1214 "Mobile tickets do not appear in Apple Wallet after a friend transfers them" vs TIX-1190 "Transferred tickets missing from the Apple Wallet pass" | 0.16 | likely duplicate (< 0.18) |
| GRO-884 "Christmas slots page says sold out" vs GRO-881 "Christmas slot booking times out" | 0.20–0.24 | related (< 0.26) |
| everything else | 0.25+ | different |

## Running it against a real Jira

The demo stores tickets and snapshots in NebulaDB. A production run would do the following:

1. **Read Jira.** Call Jira Cloud `GET /rest/api/3/search/jql` with the JQL shown under *Monitor settings*, `fields=summary,status,assignee,components,customfield_10342` and `expand=changelog`, then upsert one ticket doc per issue.
2. **Store the snapshot.** Write one snapshot doc per project per run (`scores` = `KEY=score;…`). This is the history.
3. **Compute and write.** Run `diff`, `facts`, the summary with its checks, `emailHtml` and `confluenceStorage`. All of these are pure functions in `agent.ts`.
4. **Deliver.** Send the email over SMTP (the tab's *Download .eml* is that message). Update the Confluence page with `PUT /wiki/api/v2/pages/{id}` using the storage-format body.

A Kubernetes CronJob (`0 7 * * 1` weekly, `0 7 * * 1-5` daily) is enough to schedule it.

We did not run a Jira pod in k3s1 for the demo. Jira Data Center needs a licence (a trial key is tied to an Atlassian account), a separate database and several GB of RAM. The agent only depends on the search-with-changelog response, which the demo data reproduces.

## Tests

`apps/showcase/src/labs/jira/agent.test.ts` covers:

- data integrity and snapshot timing (a 07:00 run sees only earlier changes);
- the diff on each story (new #1, rank slip, a daily spike the weekly run smooths over);
- the SQL rules;
- the corpus round-trip through SQL rows;
- the number, citation and direction checks, including a ticket title that contains a direction word and "with a score of 50" not counting as a score move;
- the facts fallback, the Confluence page and the email HTML.
